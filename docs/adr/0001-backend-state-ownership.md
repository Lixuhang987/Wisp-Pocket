# 后端按状态归属与生命周期划分边界

各项原则已在 [实施规格 #2](https://github.com/Lixuhang987/Wisp-Pocket/issues/2) 中落地。当前所有权见 [后端状态归属](../backend-state-ownership.md)；本文保留决策理由与明确排除的能力，Issue #3 沿用这些边界；后续 Issue #1 在相同所有权下增加持久 pending 输入与 snapshot 待答请求恢复，因此本文对原实施范围的排除不表示当前缺少这些能力。Issue #7 已将下文历史记录中的 Workspace 替换为 Pet，并移除 Workspace 选择请求；随后 #9 恢复独立 Workspace 并移除后端 Pet；#10 移除工具激活与 builtin Tool 配置，改为每轮目录解析与 Codex 委托。下文相应表述只保留原重构的历史范围，当前字段与流程以 owning 模块为准。

重构覆盖整个后端，包括 Thread 执行、协议接入、持久化、Tool / Provider、交互请求和服务生命周期。默认保持现有用户行为；发现矛盾时单独决策，不借结构调整改变产品规则。

后端只在一处拥有已加载 Thread 的注册表。各模块可以直接使用同一注册表，不为逐层传递它增加包装类；全局引用或参数传入按实际需要选择。依赖约束以状态归属、方向和公开边界为准，不强制只能调用相邻层，以免制造不承担职责的转发。

每个 Thread 运行实例统一管理输入队列、当前 Turn、Thread 专属工具状态及待处理请求，并协调恢复、写入和关闭。内部可以拆分模块，但外部不再分别维护 runtime、queue 和 active Turn 的生命周期。数据库、共享 MCP client、配置和连接订阅由各自模块拥有，不随单个 Thread 一并释放。

注册表允许直接查找和调用 Thread；创建和移除必须经过唯一的生命周期入口。Thread 内部状态通过有业务含义的操作修改，外部不得直接赋值执行状态或绕过清理删除注册项。持有同一对象的引用不等于拥有它；所有权依据修改和释放职责判断，而非是否存在 class 成员。

同一 Thread 的输入、中断、回执和关闭由 Thread 自己协调先后与合法性，调用方不承担加锁或检查运行状态的职责。短暂的状态变更串行处理，模型与工具执行不阻塞控制操作；不能让中断和审批回执排在整个 Turn 完成之后。此原则不改变现有输入排队等用户行为。

Thread 注册表、运行实例和业务规则放在 core；agent-server 负责连接、协议转换、依赖创建和服务启停；thread-store 负责数据库读写。Thread 通过实际需要的存储、模型和工具接口使用外部能力，不为完整包装底层 API 增加抽象层。

注册表同时保留正在执行 Turn 和等待输入的 Thread；Turn 结束不移除 Thread。冷启动恢复同样通过唯一加载入口把 Thread 加入注册表。连接断开只移除连接和订阅，不中断 Thread；这是已确认的现有行为变更。

本轮不主动卸载等待输入的 Thread。后续考虑半小时无输入后移出注册表；具体计时起点、活动任务保护和恢复合约尚未确定，不作为本轮默认实现。

无交互连接时，权限审批与 Workspace 选择仍按现有 60 秒上限等待，超时分别拒绝执行和取消选择。本轮不新增窗口重新接入后的待答请求恢复。

Thread 不再拥有临时授权记忆；权限范围与工具级匹配见 [权限决策](./0002-tool-permission-memory.md)。待处理审批请求仍由 Thread 管理。

冷启动从持久化历史恢复 Thread；加载后由 Thread 管理运行所需的内存历史，新的输入和执行结果由它统一接收并持久化。后续 Turn 使用该 Thread 的内存状态，不再每轮重新读取数据库拼装运行状态。其他模块不得绕过已加载 Thread 修改其持久化历史。

数据库承担持久保存与冷启动恢复，不承担运行控制。界面消息和模型上下文可以从历史派生；这一选择不要求改成新的事件溯源存储格式，也不要求两种派生表达相同。

流式内容可以先展示；输入持久化成功后才确认接受并执行，最终结果持久化成功后才通知成功完成。写入失败必须报告错误并停止该 Thread 的后续执行，恢复到一致状态后才能继续。失败报告不能以数据库再次写入成功为前提。

删除 Thread 时先拒绝新输入，取消执行与待答请求，协调已有写入结束，再删除历史并移出注册表；删除失败不得报告成功。关闭后端时先停止接收操作，中断各 Thread 并保存可保存的记录，再释放共享连接和数据库；保留历史，重启不自动续跑。

清理有等待上限。不能及时取消的工具可能仍产生外部效果，但晚到结果不得修改已关闭 Thread 或重新创建已删除历史。

## 状态所有权落点

| 所有者 | 拥有的状态 | 边界 |
| --- | --- | --- |
| core 的 Thread 注册表模块 | 已加载实例及唯一加载、创建和移除入口 | 直接提供查找与生命周期操作，不增加纯转发类 |
| core 的 Thread 运行实例 | 内存历史、输入队列、当前 Turn、待答请求、工具激活与组合状态、跨 Turn summary 协调 | 统一修改、并发协调、恢复与关闭；运行状态直接从这里读取 |
| Turn 执行部分 | 本轮模型与工具循环、取消信号、临时结果 | 受所属 Thread 管理，不另建全局 Thread registry |
| agent-server 的连接与 Provider 适配器 | 订阅、发送通道、Provider 身份和传输请求关联 | 不拥有 Thread 运行状态；Provider 断线仍按现有规则结束对应工具调用 |
| 后端共享服务 | 模型与工具配置、MCP client、Workspace、永久权限、Blob 服务 | 各自拥有共享缓存和资源，由后端启动与关闭流程管理 |
| thread-store | 数据库、写入顺序和持久化句柄 | 不控制 Turn；已加载 Thread 的历史写入从 Thread 发起 |
| 通知与 Activity | 对外消息和展示投影 | 不从通知反推运行事实，也不反向控制 Thread |

## 结构调整原则

- 合并 Agent owner 外壳与 Orchestrator 的实际 Thread 状态；移除外部 `runtimeByThread` 等分别管理同一 Thread 生命周期的路径。
- 保留协议路由的解析与翻译职责，将创建、恢复、排队、中断、删除等业务规则移入 core 的唯一生命周期入口或 Thread。
- 将组合根中的历史恢复、工具激活恢复与运行准备移到 Thread 管理的流程；组合根只创建、注入和释放依赖。
- 模型与工具循环保留独立职责；现有未接生产的 AgentRunner 等旧抽象不得继续形成另一套 Thread owner。
- core 内的业务逻辑与具体文件、Provider 适配明确分目录和依赖边界；不为形式分层增加包或把底层 API 完整包装一遍。
- 保留实际承担 SQLite 写入顺序、协议翻译和共享连接生命周期的模块；不以调用透传或出现 Map 为唯一删除依据。

## 默认保持与本轮边界

- 未明确改变的输入排队、配置热更新、模型与工具调用、历史格式及重启后不自动续跑行为保持现状。
- 交互请求保留向合格订阅连接发送、第一份有效请求答案生效的现有语义；本轮不引入唯一应答窗口。
- 权限规则变化需要同步 Web 审批入口、协议和 Swift 设置的展示与撤销；不扩展到其他前端重构。
- 半小时空闲回收和窗口重连后的待答请求恢复不属于本轮实现。
