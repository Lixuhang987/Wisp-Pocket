# 多桌宠 A「口袋对话」实现规格

状态：本地待实现 spec；2026-10-02。仅保存本地，未发布 GitHub Issue，未实现产品能力。用户已确认测试边界和实现前九项决定；角色 / 文件根快照与静态图方案已确认，图片导入限制为工程默认。

实现前决定见[决策记录](./implementation-questions.md)；共享输入与文件读取遵守 [ADR 0004](../../../adr/0004-context-history-default-tools.md)，不再保留旧分阶段规则。

## 问题陈述（Problem Statement）

用户希望自由创建多个有不同角色提示词和图片的桌宠，各自承载多段对话，并在 A「口袋对话」中直接交付资料、回复和找回历史。当前单宠跟随全局最新创建的 Thread，Workspace 承担文件根与历史分组，不能表达“同一文件夹、不同桌宠、各自对话”。只增加角色窗口或把侧栏标题改名，会让首轮输入、角色提示、文件工具和重启恢复继续采用旧归属。

## 解决方案（Solution）

后端将 Workspace 领域实体与注册表直接改为桌宠 `Pet` 与 `PetRegistry`，桌宠持有稳定身份、名称、角色提示词、图片和一个 `rootPath`；一个桌宠拥有多个 Thread，Thread 按 `petId` 区分。不同桌宠允许同名、同图、同 `rootPath`，仍是不同身份；共用文件根意味着读写同一批文件，不自动共享对话、附件上下文或记忆。

采用 A「口袋对话」，保留现有 surface 交互：点击桌宠唤出并聚焦输入框、展示最新消息；仅 hover 对话区展示当前 Thread 的全部历史消息，移出立即回常态并保留输入焦点 / 草稿。新增本宠 Thread 选择入口，不改变消息显隐与浏览状态。本次只实现用户自由创建的 N 个桌宠同屏，各宠独立显示和交互；三宠只是验收样本。保留同一个 Thread / Runtime / SQLite 历史体系，不建立另一套桌宠会话库，不提供跨宠物转交。

## 用户故事（User Stories）

1. 作为用户，我希望创建自己的桌宠，以便按工作方式组织对话。
2. 作为用户，我希望创建第 4、第 5 只及更多桌宠，以便不受预设三角色限制。
3. 作为用户，我希望为每宠填写名称和角色提示词，以便表达它应怎样帮助我。
4. 作为用户，我希望为每宠选择图片并预览，以便辨认交付对象。
5. 作为用户，我希望导入后移动或删除源图片仍能显示桌宠，以便配置长期可用。
6. 作为用户，我希望同图或同名桌宠仍可分别选择，以便复用外观而不混淆身份。
7. 作为用户，我希望给桌宠直接指定 rootPath，以便无需再管理独立 Workspace。
8. 作为用户，我希望多宠共用 rootPath，以便用不同角色处理同一目录的资料。
9. 作为用户，我希望了解共用文件根的效果，以便不误以为聊天记录也会共享。
10. 作为用户，我希望创建、保存失败保留表单，以便修正后重试。
11. 作为用户，我希望编辑名字和图片保留历史，以便调整形象而不失去工作。
12. 作为用户，我希望改提示词和文件根时知道适用范围，以便旧任务不突然改变行为。
13. 作为用户，我希望指定默认桌宠，以便新安装有确定的起始对象。
14. 作为用户，我希望没有历史也能点击桌宠输入，以便直接开始聊天。
15. 作为用户，我希望首次发送才创建 Thread，以便打开回复框不产生空历史。
16. 作为用户，我希望在一宠下新建多段 Thread，以便分开不同话题。
17. 作为用户，我希望从本宠入口选择旧 Thread，以便准确续聊。
18. 作为用户，我希望列表和对话显示所属桌宠，以便共用目录时仍分清历史。
19. 作为用户，我希望后台事件不切走正在编辑的 Thread，以便继续当前输入。
20. 作为用户，我希望在不同宠的窗口编辑、切历史和收起后恢复草稿，以便不丢未发送内容。
21. 作为用户，我希望多宠同屏时分别移动、缩放和交互，以便按桌面空间安排。
22. 作为用户，我希望隐藏宠收到权限请求时重新显示在桌面，以便处理需要我决定的任务。
23. 作为用户，我希望拖到角色新建、拖到对话追加，以便明确材料进入哪段 Thread。
24. 作为用户，我希望异步接收后仍投递给松手时的对象，以便转去操作另一宠不会错投。
25. 作为用户，我希望交付原文件路径后由模型按需直接读取，以便首轮即可处理任务而不强制等待第二条回复。
26. 作为用户，我希望执行中也能提交后续输入，以便由后端保存并排队。
27. 作为用户，我希望接收失败保留输入并显示原因，以便区分未提交与已保存读取失败。
28. 作为用户，我希望紧凑区能直接回复并操作建议，以便完成常见短交互。
29. 作为用户，我希望 hover 后浏览当前 Thread 全部历史、移出后回到最新消息且继续输入，以便沿用已有的轻量交互。
30. 作为用户，我希望审批说明宠、Thread、工具和真实范围，以便决定是否允许。
31. 作为用户，我希望停止明确的当前 Turn，以便中断对应任务并理解宿主取消边界。
32. 作为用户，我希望触发器指定目标宠，以便后台输入有确定归属。
33. 作为用户，我希望重启后恢复宠、历史、图片和原角色设定，以便持续处理工作。
34. 作为用户，我希望窗口失效后可重新召回，以便多屏、隐藏或崩溃不让任务失联。

## 实现决定（Implementation Decisions）

- **替换领域模型**：Workspace 的实体、注册表、设置、协议、历史归属及文件工具全部按 Pet 语义改造；不同时保留 Pet + Workspace 两个业务容器。
- **身份与历史**：Thread 必须有唯一且不可转移的 `petId`；名称、图片与 rootPath 均不能作为归属键。角色提示和文件根在 Thread 创建时保存快照。
- **后端约束**：相对路径从 Thread 的文件根快照解析；file.read 默认开放、允许任意路径且免 Permission，file.write 仍受该文件根与既有 Permission 限制。模型不能另传 petId / workspaceId 改换写入边界。
- **唯一所有权**：PetRegistry 拥有桌宠配置，ThreadRegistry / Thread 拥有执行和历史，Electron 管窗口，renderer 管导航与草稿，Swift 管系统入口；所有桌宠共用后端与全局配置。
- **交互与恢复**：仅明确用户导航改变 Thread 选择；最终 drop 固定接收对象，关闭 / 隐藏只改展示。Permission 请求使隐藏宠重新显示；同宠其他 Thread 不自动切选。
- **保留 surface 合约**：点击唤出 / 聚焦、常态最新消息、hover 全部当前 Thread 历史、移出收起不变；新增 Thread 列表只负责选择对话，不引入固定消息面板。
- 完整数据、命令、编辑与破坏性替换合约见 [数据与协议](./data-and-contracts.md)；完整 A 方案、窗口和输入合约见 [交互与入口](./interaction-and-entrypoints.md)。

## 测试决定（Testing Decisions）

- 用户于 2026-10-02 确认：优先复用现有桌宠入口 → `/api/thread` → 真实 Thread / Runtime → SQLite 用例边界；只有模型与外部传输使用可控替身，不模拟另一套业务 owner。
- 测试判断用户可观察行为、真实模型请求内容、持久化结果、文件产物与恢复语义；不锁定内部函数调用次数或组件拆分。优先扩展既有 pet-conversation / thread-ownership 主路径，少量 renderer / IPC / Settings 测试只补其独有边界。

## 非目标（Out of Scope）

- 跨宠物转交、群聊、自动协作、共享会话或把已有 Thread 改归另一宠。
- 独立 Workspace / Project 实体、一宠多文件根、每 Thread 自由选择另一宠文件根、共享知识库与自动跨 Thread 记忆。
- B「桌面长桌」、独立 C 产品形态、固定消息展开面板、语音、角色生成、外观市场、任意动画包标准、每宠模型 / 密钥 / 工具白名单。
- 新的队列暂停协议、远程 Dynamic Tool cancel、跨进程文件版本合并、全局前台资源仲裁、99% 任务成功率承诺及重做全产品设置。
- 消息阅读状态、阅读时间 / 游标、相关提醒计数本次不实现，不预留其运行逻辑或持久字段。
- 宠物归档 / 恢复、旧数据迁移 / 旧 API 兼容、桌宠截图 / 剪贴板图片及无路径图片接收；重启后的排队消息策略单列 TODO，不新增队列清理或恢复控制协议。
- 发布 Issue、实现代码、运行真实任务和变更用户实际配置不属于本次本地 spec 交付。

## 补充说明（Further Notes）

更关键的问题是：**对话归属与文件根职责需要分清。** 共用 rootPath 能共享文件内容，但不能合并历史；rootPath 决定相对路径基准和内置写入范围，读取工具免确认且可读任意路径。角色提示词能改变模型表达，其他工具权限仍由后端决定。快照保证编辑桌宠不改变旧任务的执行上下文，名称和图片仍可即时更新展示。单后端与独立前端的设计边界以 [根架构](../../../../handAgent.md) 为准；本规格只规定桌宠前端体验，共享协议变化仅要求其他消费者做必要适配。

调研采纳、明确覆盖的旧提案、当前代码证据和阅读路径见 [依据与实施路由](./evidence-and-routing.md)。三只示例、所有研究统计和模拟原型都不能作为生产能力或性能承诺；任何当前 glossary 更新须在实现落地时同步完成。
