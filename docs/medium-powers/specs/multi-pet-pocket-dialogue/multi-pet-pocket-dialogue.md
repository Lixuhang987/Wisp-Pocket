# 多桌宠 A「口袋对话」实现规格

状态：本地待实现 spec；2026-10-02。仅保存本地，未发布 GitHub Issue，未实现产品能力。用户已确认测试边界；角色 / 文件根快照、归档和图片导入细则是为可执行性补齐的默认决定。

## 问题陈述（Problem Statement）

用户希望自由创建多个有不同角色提示词和图片的桌宠，各自承载多段对话，并在 A「口袋对话」中直接交付资料、回复和找回历史。当前单宠跟随全局最新创建的 Thread，Workspace 承担文件根与历史分组，不能表达“同一文件夹、不同桌宠、各自对话”。只增加角色窗口或把侧栏标题改名，会让首轮输入、角色提示、文件工具和重启恢复继续采用旧归属。

## 解决方案（Solution）

后端将 Workspace 领域实体与注册表直接改为桌宠 `Pet` 与 `PetRegistry`，桌宠持有稳定身份、名称、角色提示词、图片和一个 `rootPath`；一个桌宠拥有多个 Thread，Thread 按 `petId` 区分。不同桌宠允许同名、同图、同 `rootPath`，仍是不同身份；共用文件根意味着读写同一批文件，不自动共享对话、附件上下文或记忆。

采用 A「口袋对话」：完整桌宠、紧凑回复、悬停浏览、显式固定展开和本宠历史入口。支持用户创建的 N 个桌宠及多宠同屏 / 单位置切换；三宠只是验收样本。保留同一个 Thread / Runtime / SQLite 历史体系，不建立另一套桌宠会话库，不提供跨宠物转交。

## 用户故事（User Stories）

1. 作为用户，我希望创建自己的桌宠，以便按工作方式组织对话。
2. 作为用户，我希望创建第 4、第 5 只及更多桌宠，以便不受预设三角色限制。
3. 作为用户，我希望为每宠填写名称和角色提示词，以便表达它应怎样帮助我。
4. 作为用户，我希望为每宠选择图片并预览，以便辨认交付对象。
5. 作为用户，我希望导入后移动或删除源图片仍能显示桌宠，以便配置长期可用。
6. 作为用户，我希望同图或同名桌宠仍可分别选择，以便复用外观而不混淆身份。
7. 作为用户，我希望给桌宠直接指定 rootPath，以便无需再管理独立 Workspace。
8. 作为用户，我希望多宠共用 rootPath，以便用不同角色处理同一目录的资料。
9. 作为用户，我希望了解共用文件根的效果，以便不误以为聊天记录也会共享。
10. 作为用户，我希望创建、保存失败保留表单，以便修正后重试。
11. 作为用户，我希望编辑名字和图片保留历史，以便调整形象而不失去工作。
12. 作为用户，我希望改提示词和文件根时知道适用范围，以便旧任务不突然改变行为。
13. 作为用户，我希望归档桌宠保留历史与真实文件，以便整理入口而不丢资料。
14. 作为用户，我希望恢复已归档桌宠，以便继续原来归属于它的工作。
15. 作为用户，我希望指定默认桌宠，以便快捷入口有确定接收者。
16. 作为用户，我希望没有历史也能点击桌宠输入，以便直接开始聊天。
17. 作为用户，我希望首次发送才创建 Thread，以便打开回复框不产生空历史。
18. 作为用户，我希望在一宠下新建多段 Thread，以便分开不同话题。
19. 作为用户，我希望从本宠入口选择旧 Thread，以便准确续聊。
20. 作为用户，我希望列表和对话显示所属桌宠，以便共用目录时仍分清历史。
21. 作为用户，我希望后台事件不切走正在编辑的 Thread，以便继续当前输入。
22. 作为用户，我希望切宠、切历史和收起后恢复草稿，以便不丢未发送内容。
23. 作为用户，我希望多宠同屏时分别移动、缩放和交互，以便按桌面空间安排。
24. 作为用户，我希望单位置切宠只改变显示，以便其他宠的任务继续且可找回。
25. 作为用户，我希望看见隐藏宠的未读与待决定标记，以便知道哪里需要我处理。
26. 作为用户，我希望拖到角色新建、拖到对话追加，以便明确材料进入哪段 Thread。
27. 作为用户，我希望异步读取后仍投递给松手时的对象，以便切宠不会错投。
28. 作为用户，我希望拖入先读取和建议、等我明确回复再执行，以便掌握任务意图。
29. 作为用户，我希望执行中也能提交后续输入，以便由后端保存并排队。
30. 作为用户，我希望接收失败保留输入并显示原因，以便区分未提交与已保存读取失败。
31. 作为用户，我希望紧凑区能直接回复并操作建议，以便完成常见短交互。
32. 作为用户，我希望显式展开后稳定查看长文、工具详情和请求，以便不依赖持续悬停。
33. 作为用户，我希望审批说明宠、Thread、工具和真实范围，以便决定是否允许。
34. 作为用户，我希望停止明确的当前 Turn，以便中断对应任务并理解宿主取消边界。
35. 作为用户，我希望在 ThreadWindow 看到同一宠的同一 Thread，以便完整查看而不重开对话。
36. 作为用户，我希望快捷输入和触发器指定目标宠，以便资料不会进入当前碰巧显示的宠。
37. 作为用户，我希望重启后恢复宠、历史、图片和原角色设定，以便持续处理工作。
38. 作为用户，我希望窗口失效后可重新召回，以便多屏、隐藏或崩溃不让任务失联。

## 实现决定（Implementation Decisions）

- **替换领域模型**：Workspace 的实体、注册表、设置、协议、历史归属及文件工具全部按 Pet 语义改造；不同时保留 Pet + Workspace 两个业务容器。
- **身份与历史**：Thread 必须有唯一且不可转移的 `petId`；名称、图片与 rootPath 均不能作为归属键。角色提示和文件根在 Thread 创建时保存快照。
- **后端约束**：文件工具从 Thread 的宠物文件根快照解析相对路径；不允许模型通过另传 petId / workspaceId 改换文件根。继续采用既有 Permission 和路径校验。
- **唯一所有权**：PetRegistry 拥有桌宠配置，ThreadRegistry / Thread 拥有执行和历史，Electron 管窗口，renderer 管导航与草稿，Swift 管系统入口；所有桌宠共用后端与全局配置。
- **交互与恢复**：仅明确用户导航改变选择；最终 drop 固定接收对象，关闭 / 隐藏只改展示，通知与请求按真正归属显示。
- 完整数据、命令、编辑与旧数据处置合约见 [数据与协议](./data-and-contracts.md)；完整 A 方案、窗口和其他入口合约见 [交互与入口](./interaction-and-entrypoints.md)。

## 测试决定（Testing Decisions）

- 用户于 2026-10-02 确认：优先复用现有桌宠入口 → `/api/thread` → 真实 Thread / Runtime → SQLite 用例边界；只有模型与外部传输使用可控替身，不模拟另一套业务 owner。
- 测试判断用户可观察行为、真实模型请求内容、持久化结果、文件产物与恢复语义；不锁定内部函数调用次数或组件拆分。优先扩展既有 pet-conversation / thread-ownership 主路径，少量 renderer / IPC / Swift 测试只补其独有边界。

## 非目标（Out of Scope）

- 跨宠物转交、群聊、自动协作、共享会话或把已有 Thread 改归另一宠。
- 独立 Workspace / Project 实体、一宠多文件根、每 Thread 自由选择另一宠文件根、共享知识库与自动跨 Thread 记忆。
- B「桌面长桌」、独立 C 产品形态、语音、角色生成、外观市场、任意动画包标准、每宠模型 / 密钥 / 工具白名单。

## 补充说明（Further Notes）

更关键的问题是：**对话归属与文件访问如何共同由桌宠确定。** 共用 rootPath 能共享文件内容，但不能合并历史；角色提示词能改变模型表达，但不能授予工具或系统权限。快照保证编辑桌宠不改变旧任务的执行上下文，名称和图片仍可即时更新展示。
