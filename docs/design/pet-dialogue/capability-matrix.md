# 桌宠主入口的能力覆盖与完成口径

状态：后续设计与验收矩阵，2026-09-14；**不是已实现清单，也不证明已达到 99%**。行为选择以 [身份与角色](./model-and-persona.md)、[交互层次](./interaction.md)、[历史与交付](./history-and-input.md) 为准；完整任务见 [端到端场景](./journeys.md)。术语引用 [Desktop Experience](../../../apps/desktop/CONTEXT.md)、[Conversation Runtime](../../../packages/core/CONTEXT.md) 与 [Host Automation](../../../apps/host-automation/CONTEXT.md)，本页不另建词表。

现状主要依据 [生产代码审计](../../research/2026-09-14-pet-codebase.md)，并复核 [ThreadWindow 界面](../../../apps/thread-window-web/src/src.md)、[Settings](../../../apps/desktop/Sources/Settings/settings.md)、[内置功能](../../../apps/host-automation/host-automation.md) 和 [manual QA](../../manual-qa.md)。例如当前 ThreadWindow 的搜索只过滤列表预览，不能记为服务端全文检索；桌宠 controller 可以发送某类回执，也不能据此认定界面有对应按钮。单宠的既往实机记录不自动证明当前多宠方案通过。

## 阶段与证据

| 阶段 | 本矩阵中的含义 |
| --- | --- |
| P0 | 建立身份、创建与恢复的贯通，以及桌宠窗口、命中、焦点和两种展示方式的原生基础。 |
| P1 | 让本宠完整对话成立：历史、资料、后续输入、运行控制、请求、结果与跨宠交接。 |
| P2 | 所有外部入口回到目标宠物，补配置、内置功能、权限管理、恢复和共享资源可靠性。 |
| P3 | 主入口承诺范围内的规模、真实系统与用户任务验收；不把仅有 UI 或原型演示的条目提前记为完成。 |

每行阶段表示最早需要交付的层次；写成 `P0→P1` 表示基础路由与完整交互分步完成。**纳入主入口范围的条目都须经过 P3 的对应验收**；C57 语音是明确列出的后续可选能力，不作为文字主链路完成的前置条件，启用时另按同等门槛验收。验证列描述应观察到的事件及结果，不承诺这些事件已被当前实现记录；协议名称仅在现有类型已定义时引用。

## 如何验证 99%，以及何时不能这样宣称

**能力可达是前置条件，99% 是尚未证明的真实任务完成目标。** 上面 60 项即使全部有按钮、自动检查通过、原型可演示，也不能推出真实完成率。一个任务按用户希望得到的结局计量；例如“读 PDF→请 Miku 写邀请→交给小八保存”是一条完整任务链，不能拆成三条成功掩盖最后保存失败。

| 指标 | 分子 | 共同分母与解释 |
| --- | --- | --- |
| 全程宠内完成率 | 成功任务中，所有 Wisp Pocket 应用内步骤均在桌宠、归属明确的会话面板、历史/管理抽屉中完成的数量。 | 预先约定观察窗口内进入观察队列的全部合格真实任务。失败、被迫回退、未完成和系统原因取消保留；重试属于原任务，不用新增成功次数冲淡失败。 |
| 无 ThreadWindow 完成率 | 成功任务中，从开始到结果核验没有依赖 ThreadWindow 的数量；可包含 PromptPanel 或独立 Settings。 | 使用同一分母。因此该比例可以高于全程宠内完成率；只能称“无需 ThreadWindow”，不能把独立设置中的操作改称宠内完成。 |
| 能力覆盖、主观体验与运行可靠性 | 分别报告矩阵逐项证据、用户亲近/控制感，以及误投、丢草稿、重复执行、错误建议识别、打断和恢复情况。 | 这些是独立质量指标，不用于替换上述真实任务比例，也不以点击量、Token 数或对话段数代替任务数。 |

系统授权对话框、原生文件选择器和用户明确打开的最终产物，作为平台/产物动作单独记录；不把它们伪装成桌宠表面，也不算成 ThreadWindow。全程宠内采用上表的“应用内步骤”口径，同时另报需要系统弹层的任务数，避免隐藏平台依赖。通过“打开设置”按钮跳到独立 Settings 完成工作，只满足较宽的无 ThreadWindow 口径。

观察前锁定任务范围、时间窗口、成功结局和排除规则；发生技术失败之后不能临时剔除该类任务。人工正常取消与目标改变单独标注并保留原记录；跨宠转交、内部重试和恢复保持同一任务关联。未到结局的任务保留为未完成，不提前记成功。报告应同时给出样本量、场景分布、观察时长与不确定性，不能拿少量全成功演示宣称达标。

原型验证信息结构、分支和目标是否清楚；协议/持久化检查验证所有权与恢复；原生测试验证实际窗口、输入、权限和跨 App 资料；真实用户试用才提供完成率与长期负担证据。每条最终验收记录须说明证据属于哪一层，全部未满足之前保持“目标/待验”。
