# 研究与原型任务书

本轮交付研究、推荐设计和一次性原型；不把原型接入生产 Agent 或改写真实用户历史。依据为用户本轮目标、[Issue #1](https://github.com/Lixuhang987/Wisp-Pocket/issues/1)、基线提交 `ca1c02b` 与 2026-09-14 现场核查。

## 要回答的问题

1. 多只桌宠怎样同时具备角色存在感和明确的交付对象，仍不遮挡工作？
2. 对话、历史、资料、权限和工作区如何围绕角色完成，使 ThreadWindow 成为可选出口？
3. 切桌宠、切历史、后台完成、改人设、重连和延迟拖入时，哪些状态可以改变，哪些必须固定？
4. “99%”的能力覆盖与完成率如何被验证，而非由界面上多放几个入口宣称成立？

## 已有证据与约定

- 用户截图为主 checkout 的 `docs/截屏2026-09-14 01.55.10.png`（920×766 RGBA），本目录保留[原样副本](./evidence/current-shape.png)。可见左下角色、右上长回复裁剪、右下输入，以及中间较大空白；无法单凭静态图推断焦点、悬停或系统命中。
- 当前 production 使用一个角色、一份当前 Thread 选择；按创建时间跟随全局最新 Thread，切换清空桌宠草稿，未提供桌宠历史选择或 Stop。实际行为证据由架构盘点记录。
- [紧凑布局方案](../../medium-powers/plans/2026-09-14-pet-compact-hover.md) 已记录用户对约 210px 对话列、44px 回复框、三行正文、悬停统一滚动、点击显示/隐藏与无历史首次输入的选择；截至基线尚未落地。
- 本设计沿用这些常态约定。需长期阅读、操作权限或浏览历史时使用显式展开/固定表面，不把更大的管理任务塞进 hover。推荐值属于后续实现目标。
- 领域规范入口：[Desktop Experience](../../../apps/desktop/CONTEXT.md)、[Conversation Runtime](../../../packages/core/CONTEXT.md)。用户所说 session 对应现有 Thread，产品界面称“对话”。Workspace 继续表示文件边界。

## 原型的共同场景

桌面上正在查看“读书交换日”活动草案。把活动 PDF 交给八千代整理资料，请 Miku 写邀请文案，再让负责执行的桌宠保存确认后的内容。每只桌宠还有其他工作区的历史与一份草稿，后台任务可以独立完成。

比较三种交互假设，而非把同屏/单宠状态充当三个方案：

| 方向 | 主要动作与信息结构 | 检验的问题 |
| --- | --- | --- |
| A 口袋对话 | 点一只桌宠，在角色旁回复；按需展开历史/工具 | 角色就地对话是否足以承接大部分工作？ |
| B 桌面长桌 | 资料在共同桌面中央，选择负责的桌宠并交付 | 高频资料交接是否值得占用更宽的横向区域？ |
| C 对话手册 | 角色引导侧边阅读面，历史与成果连续展开 | 长文和多次决定是否需要稳定的阅读空间？ |

每个方向都提供“全部同屏 / 单个位置切换”显示方式；所用内容、角色与业务动作相同，避免用不同样例制造优劣。

## 素材与运行边界

- 产品外观遵循根 `DESIGN.md`；UI 原型与原生实验直接引用 `apps/thread-window-web/src/styles/generated-theme.css` 的变量，不另造品牌或覆盖生产 token。独立状态模型为可单文件运行的工具，冻结了少量现有 token 值，属于隔离原型的快照，不是新的生产主题源。
- 主要角色使用现有 `apps/electron-shell/src/activity-window/assets/yachiyo.webp`；动画仅复用 `PetSprite.tsx` 已核实的行与帧时长。
- 第二形象取用户本地 `~/.codex/pets/miku/spritesheet.webp` 的首帧作为静态预览，原路径和 hash 在原型素材索引保留。第三档案复用八千代外观，以验证“外观可相同，身份和提示不同”；不把它宣称为新角色资产。
- 原型背景是由活动草案、文件列表与窗口 chrome 组成的示例桌面，不复制用户工作内容。示例文字为本次编写。
- 原型模拟资料读取、模型回复和文件保存；不接真实服务、API Key 或文件写工具，内存状态可重置。
- 浏览器只能验证原型动作、布局和状态；跨 App drop、Spaces、多屏、IME、系统焦点和 VoiceOver 需要代表性的原生实验/验收，另列门槛。

## 执行与完成标准

先核对代码与外部来源，再比较 UI 方向，最后用独立状态模型演示延迟拖入、隐藏后台请求与角色提示修订等困难情境。每个完成结论须有对应浏览器操作、截图、源文档或代码证据；推荐不冒充真人可用性结论。

文档收尾由未继承上下文的独立 agent 核对设计、代码、目录指南与 manual QA，再执行提交。
