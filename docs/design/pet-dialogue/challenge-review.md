# 多桌宠方案的独立反例审查

日期：2026-09-14。范围：基于本工作树 `docs/design/pet-dialogue/brief.md` 的 A 口袋对话 / B 桌面长桌 / C 对话手册，以及“每个 Thread 归一只宠物、Workspace 可选、三宠完整展示与单槽共存、默认单一展开但可固定多个、后台不抢当前”的推荐。这里的反例用于修正规则，不是宣称现有代码已经发生这些缺陷；没有启动原生 App。平台事实见 `docs/research/2026-09-14-pet-platform-hci.md`。

审查结论：推荐成立的前提是 **交互入口、执行对象和结果归属都由宠物身份贯穿**。可见数量、输入焦点、历史归属与宿主执行权不能合成一个“当前宠物”变量。以下门槛是待满足的设计 / 验收标准，不是已测结果。

## 先约束三个方向的比较方式

| 方向 | 不能掩盖的反例 | 保留该方向的条件 |
| --- | --- | --- |
| A 口袋对话 | 三行正文里放不下完整授权范围；为了保留小尺寸，每次需要看代码/差异/成果就被送回 ThreadWindow。 | 小尺寸负责随手问答，显式展开后在同一角色上下文内完成长文、证据、决定、历史与成果；不能把“有打开工作台按钮”算该能力已由桌宠承接。 |
| B 桌面长桌 | 公共材料台逐渐变成全局任务管理器，用户看不出材料给了谁；三个角色只是装饰头像。 | 每次资料交付都有一个显式接收角色与会话，公共摆放不自动等于授权所有角色读取。长桌收起后任务与宠物仍可独立继续；其额外空间成本必须通过同任务比较体现。 |
| C 对话手册 | 一个固定侧栏承包所有交互，桌宠只负责打开它；旧 ThreadWindow 更名而行为不变。 | 手册由角色进入、始终标明归属、可从角色继续未完成决定，关闭后回到原宠物；长阅读面是宠物的展开表面。避免增加第二套“当前 Thread”与全局新建入口。 |

三种方向都必须提供三宠完整展示和单槽模式、同样的任务/资料/人设/延迟/错误、相同的权限与停止能力。不能让 A 测短回答、C 测长报告，再以不同任务结果下结论。推荐以 A 为日常入口，吸收 C 的持久展开阅读，把 B 作为显式多角色交接时的可选布局；该组合仍需原型比较，不是研究已经证明的赢家。

## 范围、99% 与身份归属

| 编号与具体反例 | 建议规则 | 可验证门槛 |
| --- | --- | --- |
| 01：输入和回复都在桌宠，但停止、权限、选工作区、错误恢复四条路径仍只能打开 ThreadWindow。 | 以“从任务开始到完成/拒绝/失败恢复的完整路径”统计能力，而不是入口数量。展开表面保持宠物归属；生产 ThreadWindow 不得作为核心回执或状态恢复的依赖。 | 建立能力×场景矩阵；每条核心路径在不调用 `openThreadWindow` 的情况下走完，并检查后端结果，不只截图按钮。若某条仍必经旧窗口，则这一能力未迁移。 |
| 02：模型设置、管理角色、录音权限修复都扔回全局设置页，却把这些动作从统计中删掉，得到 99%。 | “功能可达性”与“真实任务无需旧窗口完成的比例”分开。设置可以是桌宠主动打开的必要辅助表面，但须明确标注仍未整合的功能，预先固定统计分母和排除规则。系统授权对话框不必伪装成桌宠 UI。 | 原型逐项演示新增角色、人设编辑、历史搜索、资料投递、读写决定、停止/重试、工作区选择与必要设置。真实使用统计保留回退和失败；没有观察数据就只报告目标，不能写已达 99%。 |
| 03：所谓三宠同屏其实是一只完整宠物加两个头像，或打开乙就自动隐藏甲。 | 完整同屏是一等显示方式：三个完整形象均可辨认并独立点击/收资料；仅“会话面展开”默认单一。固定多个会话面须真实可并行看结果。 | 三只同时可见；依次向三者投递、打开历史、固定会话；至少一只在后台运行。全程证明没有隐式降成单宠模式。 |
| 04：第二、第三档案使用相同皮肤，角色名只在 hover 出现；用户把重要资料投给了错误人设。 | 皮肤不是身份主键。完整展示时保留足够的姓名/角色区别，接收、输入、审批、成果处持续标明角色；单槽隐藏角色也能按名称定位。 | 在同皮肤情境下执行指定对象投递、历史恢复与授权，记录误投和纠错；测试脚本每次接收与提示中的角色标识一致，不能只验证不同颜色时可辨认。 |
| 05：一只宠物开心地蹦跳，但一个对话在失败、另一个在等批准，用户把情绪当执行状态。 | 人设/装扮、社交表情、任务状态三层分开。宠物级摘要允许“2 项运行 · 1 项待确认”；焦点会话状态不可覆盖其他未处理状态。 | 同一宠物有不同状态会话时，能从其入口找齐所有未决事项；关闭动画、声音或颜色后，运行/等待/失败/完成仍可区分。 |
| 06：Thread 永久归甲，但用户说“让乙接着写”；实现直接修改 Thread.petId，旧对话像是一直和乙聊的。 | 保持历史归属。交接创建乙的新对话，附显式选定的材料/摘要与来源链接；原对话不改名换主人。若调用其他角色协作，记录协作者身份，不把内部子任务默认当另一只桌宠的个人会话。 | 交接前后原历史的主人、引用、权限回执不变；乙只得到交接范围；用户能回到原对话查来源，不能悄悄搬走完整记录。 |
| 07：用户改人设时甲正在执行；后半任务突然用了新提示词，历史又只显示当前配置。 | 按[角色快照规则](./model-and-persona.md)在 Thread 创建时固定实际角色提示及版本；旧对话继续使用原快照，采用新设定须明确带摘要新开对话。外观修改不改变提示；工具撤销仍按当前后端限制立即生效。 | 在运行中改名、换皮、改提示、撤销工具、切槽；旧 Thread 恢复后仍使用创建快照，新 Thread 使用新版本，被撤销的工具不因旧快照重新获准。 |

## 窗口、焦点、鼠标、键盘与语音

| 编号与具体反例 | 建议规则 | 可验证门槛 |
| --- | --- | --- |
| 08：为容纳三宠，用一个全屏透明罩；看起来没背景，却拦住下面编辑器的选字和链接。 | 控制真实窗口覆盖范围和命中区域。每宠小窗、每显示器受控舞台等方案先做原生比较；不以 alpha=0 视为穿透。捕获框只覆盖当前交互目标，不让隐形拖入区无期限占据桌面。 | 三宠远离/重叠、气泡开关、快速鼠标移动、renderer 掉帧时，后台文字可选、链接可点、宠物可命中；记录鼠标事件与窗口矩形，不接受纯网页截图作为证据。 |
| 09：整只宠物都用了 `app-region: drag`；能搬动，但点它不出输入，拖 PDF 没响应。 | 明确移动手势与点击/投递的界限。按钮与接收区保持 no-drag，移动用手柄或单独识别的手势；拖资料不启动搬家。 | 同一只宠物依次单击、双击/长按（若支持）、移动、接收文件、点菜单，动作不串线；逐项用实际 Electron 窗口验证。 |
| 10：用户在编辑器打字，乙完成任务打开输入面；随后几个字进入乙，用户并未看见焦点变化。 | 后台完成、进度、hover、单槽未读更新不调用聚焦。只有用户的明确输入意图授予键盘目标，收起需验证归还焦点；不能把 `setFocusable(false)` 当作归还已完成。 | 在外部 App 持续输入期间让三宠同时完成/失败/待确认；前台和字符落点不变。然后主动打开宠物并收起，确认前台恢复与字符连续性。 |
| 11：输入“会议纪要”的拼音还没选字就切宠，草稿被清空，Enter 又把半成品发给新宠。 | 草稿按宠物+会话保留。IME composition 未完成不把 Enter 当发送；切换前保存组合输入的语义，必要时等待 compositionend 或取消切换动画，不能以 DOM 卸载决定结果。 | 中文/日文输入法、组合中切宠/切历史/收起/窗口失焦逐项测；无误发送、无丢失、无跨对象草稿。可在原型模拟草稿逻辑，IME 门槛必须原生通过。 |
| 12：语音转文字很慢，用户对甲开始录音，切乙后识别完成，指令自动发给乙。 | 在开始一次录音时绑定目标，整个 utterance 不跟随显示槽位。明确展示“正在对甲说”，语音录入与发送意图分开；切宠可以保留或结束录音，但不能改投。 | 延迟 ASR、录音中切宠、权限拒绝、取消、网络断开、隐藏宠物均模拟；最终文本只进原目标或明确的恢复暂存区，取消不会发送。 |
| 13：三只都“听着”，背景谈话意外触发执行；停止一只语音又关闭另外两只任务。 | 麦克风是共享输入资源，默认同一时刻一个显式录音目标；选择语音与运行任务分离。没有必要把唤醒词/常听作为核心完成条件；不默认监听环境。 | 界面与系统麦克风指示一致，录音开始/停止/目标可解释；所有主要能力可用键盘完成。无语音用户不能被迫打开 ThreadWindow。 |
| 14：三宠在外接屏，拔掉屏幕后它们和“显示全部”入口一起消失；窗口又位于菜单/Dock外。 | 持久化相对锚点并监听显示器变化，恢复到可用区域；保留菜单栏/快捷键召回作为桌宠自身的兜底。全屏、Spaces、Stage Manager 策略与显示方式独立。 | 热拔、混合缩放、负坐标、Dock换边、显示器ID变化、系统睡眠后每只宠物仍可召回。全屏策略明确，不能为了保证可见而压住系统授权对话框。 |

## 投递、历史与工作区

| 编号与具体反例 | 建议规则 | 可验证门槛 |
| --- | --- | --- |
| 15：拖进甲，拖到乙再松手；异步附件物化时用户又切回甲，结果发给第一次 hover 或最后当前的对象。 | hover 仅是候选；成功 drop 时固定接收宠物、会话/新会话与资料标识。随后物化、解析、重试都用该投递记录，不能再查全局 currentPet。 | 测“甲→乙松手→丙切换→物化完成”等排列；实际接收只在乙且一次。目标删除/归档时显式待处理，不改投最近活跃宠物。 |
| 16：B 长桌的一个 PDF 看起来归甲，三个宠物却都能读到；共享工作区被当作共享全部聊天记录。 | 材料存放位置与向角色交付是两件事。共享材料明确授权范围；workspace 文件可见性和 conversation 历史读取分别建模。转交只带用户选择的材料与必要摘要。 | 向甲给一个专属材料，乙正常运行时不能因共享长桌或工作区收到它；主动分享后可查交付记录。不同工作区的历史检索也不在发送时静默混合。 |
| 17：用户只想问一句话却被强制建工作区；反过来“不选工作区”时保存结果写进一个隐式上次目录。 | 无文件任务允许无 workspace；附件可在该对话的材料范围内处理。需要文件边界时在当前宠物内解决，显示将作用的明确路径；无上下文时不默认复用另一宠物目录。 | 无工作区完整完成纯问答、图片解释；需要保存时在宠物内选择并显示范围。取消选择后不写文件，原草稿与任务可继续。 |
| 18：切到历史会话只是换标题，回复仍提交给最新创建的 Thread；关闭后再开又自动跟到别宠的新 Thread。 | “选中会话”与“全局最近事件”分离。每宠最近选择和草稿独立；状态恢复必须从已绑定 Thread 的 snapshot 获取，不因其他宠物新建而抢当前。 | 甲旧对话输入，同时乙新建/完成，甲关闭重开、Electron重连；主人、会话ID、草稿、审批和下一条消息路由全一致。 |
| 19：甲说“我记得你上次的病历”，只是检索了另一个工作区历史；用户以为每宠独立会话就是隐私隔离。 | 将历史记录、可选跨会话记忆、工作区材料、长期偏好分开解释。独立记录不自动承诺强安全边界，也不自动授予跨历史读取。记忆条目可查看来源、范围和删除效果。 | 构造同宠不同工作区、不同宠同工作区两种敏感记录；当前回答只能按正式设计声明的范围获得上下文。删除会话与删除衍生记忆的效果可分别验证。 |

## 并行执行、宿主冲突与请求恢复

| 编号与具体反例 | 建议规则 | 可验证门槛 |
| --- | --- | --- |
| 20：甲根据截图点“保存”，乙同一瞬间切到邮箱；甲实际点中了“发送邮件”。 | 共享桌面的观察→交互需要同一 Host 资源仲裁。模型计算、独立读取可并行，前台 UI 操作不能由三套宠物锁各自认为独占。失去/重获宿主执行权后重新观察，不复用过期坐标。 | 在三宠交错动作与人工切App下，只有一个合法控制者执行键鼠；等待者显示“等候桌面控制权”，可取消且不会永远饥饿。通过原生焦点/截图/工具事件日志证明，不以各自session独立代替。 |
| 21：甲和乙都给同一工作区生成 `邀请函.md`，最后保存者覆盖前者；两个任务都显示成功。 | 区分共享前台控制权与文件写冲突。独立I/O可以并行；同目标写入需要版本/前置条件或合适的资源锁，冲突变成明确的重算/另存/确认，不能静默丢结果。外部人工修改也要在范围内。 | 两宠写同文件、同目录不同文件、人工改文件、任务重试分别测。无丢失更新和假成功；保存结果能指回实际产物与版本。任意shell副作用不能假装已被路径锁完整覆盖。 |
| 22：丙被隐藏，但它的权限请求一直等不到；为避免死锁，系统定时自动允许。 | 未决请求是全局可达且归属明确的任务事实，隐藏不解决请求。当前宠物可提示数量并直达原宠物，通知不自动切当前输入；首个切片保留现有 60 秒时限，超时不授予权限，重新检查后才能发起新请求。 | 单槽只显示甲时让乙/丙待确认，能在桌宠入口发现和处理；断网/重连区分仍有效和已过期请求，后端只接纳一次有效回执；拒绝、超时与中断的结果可查，旧 requestId 不复活。 |
| 23：用户点“收起来”以为暂停；另一个地方点Stop只停动画；文件还在被写。 | 收起/隐藏、取消排队、停止运行、停止录音、退出App各用明确语义。停止状态来自实际取消结果，必要时显示“正在停止”，并说明已经完成的外部效果。 | 在模型流式、工具运行、宿主排队、权限等待四阶段测试停止；对照后台事实与产物。停止一宠不取消其他宠的独立任务，UI关闭也不伪称取消成功。 |
| 24：某只桌宠 renderer 崩溃重建后显示 idle；健康后端仍执行，其中一项权限被重复提交。 | 运行、历史、请求由权威后端恢复；窗口状态恢复不得重放具有副作用的用户输入。恢复时允许短暂“正在同步”，不得以无动画表示无任务。 | 分别测试 renderer 崩溃、整个 shell/服务重启、连接中断和睡眠；按实际进程存续恢复，过期请求不复活，无重复提交或双回执，隐藏宠物的待决定结果和未读也能找回。 |

## 安静、权限与可访问性

| 编号与具体反例 | 建议规则 | 可验证门槛 |
| --- | --- | --- |
| 25：三宠同时完成，各弹出长气泡、播放声音、跨屏跳到当前工作旁；因为叫“同事”所以总能打断。 | 一个提醒调度点，按任务紧急程度合并；普通完成默认摘要/未读，详细内容由用户打开。Focus/安静模式、演示与手动隐藏策略明确，不假定OS自动治理自绘气泡。 | 外部App输入、全屏演示、手动安静、系统Focus时触发混合事件；无抢焦点、无不必要内容泄露，待确认保持可达。研究中更喜欢角色不能为中断开绿灯。 |
| 26：温柔角色用“信任我吧”盖住按钮，删除/外发范围缩成一行；用户为了让它高兴而允许。 | 权限事实和决定控件保持中性、完整、可展开核查；角色语气可围绕请求，但不能修改scope、淡化后果或以情绪奖惩诱导同意。已有授权可继续，避免重复确认疲劳。 | 同一动作换三种人设，展示的真实目标、后果、默认选择和执行边界一致；拒绝后正常协作。角色不能生成或替换系统授权结果。 |
| 27：开启Reduce Motion后关掉精灵动画，也把“正在等待”的唯一提示关掉；VoiceOver只能听见三次“图片”。 | 不把动画/音效当功能通道。每宠有名称、状态、动作语义；全键盘与辅助技术覆盖输入、历史、投递替代、选择工作区、批准/拒绝、停止和结果。 | 关闭所有动画和声音，启用VoiceOver/高对比度/放大文字，仍完整走通核心能力；不能把需要无障碍的人推回ThreadWindow才完成。 |

## 必须进入主设计的收敛规则

1. 不建立一个含糊的 `currentPet` 同时承担显示、键盘、语音、drop、Thread归属、后台请求路由与宿主执行权；分别记录这些目标，并定义改变的触发时刻。这里是状态职责建议，不指定生产协议字段名称。
2. 用两个不同的固定时刻避免错投：语音在一次录音开始时固定对象，材料在成功 drop 时固定对象；键盘在明确进入编辑时绑定当前输入控制器，切换前保存草稿。
3. 让宠物成为任务归属的持续锚点：长阅读面、历史、必要设置可以展开，但核心任务的决定、停止、恢复与成果不得依赖原ThreadWindow；统计和原型要证明完整链路。
4. 显示方式与窗口粒度分开决策：三宠完整同屏不等于一个全屏窗口，单槽也不等于后台只许一个任务。用原生事件与能耗比较决定窗口实现。
5. 后端多会话并行不能绕过共享资源仲裁。先明确前台控制权、文件冲突、权限请求与用户手动接管的边界，才宣传多只宠物同时帮忙。

建议先用交互原型逼出上述状态错误，再做覆盖关键原生行为的最小实验，最后招募用户比较同一组任务。示意图通过、脚本路径通过、真实系统通过和真实用户长期采用是四种不同证据，不能互相替代。
