# 以桌宠为中心的 Wisp Pocket

状态：**研究与设计提案，2026-09-14；新增生产能力尚未实现。** 本轮以 [Issue #1](https://github.com/Lixuhang987/Wisp-Pocket/issues/1)、用户提供的当前截图和基线提交 `ca1c02b` 为依据，交付中文设计、来源研究与一次性原型。推荐方案由自主质询形成，不冒充用户已经确认的选择或真人可用性结果。

推荐把产品的基本动作变成：**找到这位伙伴 → 把话或材料交给它 → 在它身边继续问、决定、拿走结果 → 下次仍能找回与它的那段对话。** 每只桌宠有自己的身份、角色提示和历史；Workspace 是可选的文件上下文，显示方式独立于身份和对话。

默认采用 **A「口袋对话」**，保留已讨论的紧凑回复框与悬停浏览；长文、历史和工具决定通过显式展开获得 C「对话手册」的稳定阅读能力。B「桌面长桌」保留为高频资料整理场景的备选。三套原型均支持三只完整桌宠同屏和单个位置切换，不把显示模式当成互斥的产品方向。

## 关键结论

| 问题 | 推荐设计 | 必须守住的边界 |
| --- | --- | --- |
| 多只桌宠究竟意味着什么 | 每只都有稳定档案；外观、名字、语气与工作提示可配置 | 相同皮肤也可以是不同伙伴；换皮肤不换历史 |
| 谁拥有一段对话 | 每个 Thread 在创建时固定所属桌宠与角色提示快照 | 新人设默认用于新对话；旧记录不被重新演绎 |
| 三宠同屏还是单位置 | 两种方式都是一等能力，共用身份、历史与运行状态 | 切换显示不停止后台任务，不清空草稿、不改变接收者 |
| 资料拖到哪里 | 角色本体创建新对话；对话表面追加当前对话；自动 inspect | 最终松手固定路由，异步读取不追随之后的选择 |
| 怎样找回历史 | 每只宠都有历史入口，按 Workspace 分组，可搜索并跨宠查找 | 切入他宠历史时同步显示真正的所有者 |
| Workspace 如何结合 | 随聊无需文件夹；工作对话可选默认 Workspace，伙伴之间可以相同 | 当前 `workspaceId` 是关联元数据，不能宣称是文件访问沙箱或共享记忆 |
| 怎么把事交给另一只宠 | 用户选择摘要、片段或附件后，创建目标宠自己的新对话 | 不静默共享全量历史；源对话不改归属 |
| 多只宠同时执行 | 模型和独立 I/O 可并发；同一前台桌面资源串行仲裁 | 两只宠不能同时抢键鼠；同路径写入要识别冲突 |
| 如何做到桌宠内闭环 | 输入、进度、停止、等待决定、工具详情、历史与成果均在桌宠表面可达 | 隐藏请求不能只剩详情窗入口；过期请求不得继续批准 |
| 怎样弱化 ThreadWindow | 先补桌宠入口，再解除启动、连接、提交和宿主能力的真实依赖 | 改名或默认隐藏不算完成；禁用/崩溃后仍须走通任务 |
| 怎样验证 99% | 统计真实任务的全程宠内完成率和无 ThreadWindow 完成率 | 60项能力覆盖只是设计检查，不能替代实际成功率 |

当前实现仍是单宠、跟随全局最新创建的 Thread，并缺少桌宠内历史选择和完整停止/详情入口。设计复用既有 Thread、输入持久化、队列与请求仲裁，在拥有职责的模块补齐身份与路由；不建立第二套“桌宠消息库”。权限 `always` 目前按全局工具名生效，Permission/Workspace 请求仍有 60 秒有效期，这些事实在设计中保留并明确展示。

## 用一个任务理解体验

把活动草案 PDF 拖给八千代。它接住资料、说明读到了什么，提醒还缺报名方式；你继续在它旁边提问，或把选定摘录交给 Miku 写邀请。Miku 用自己的工作提示起一段新对话，源资料标明来自八千代。文案确认后交给小八；小八展示准确的文件名、目标位置和待写内容，再按有效授权执行。保存成功才出现可打开的实际成果。

过程中可以随时改聊另一只宠、浏览历史或隐藏面板。后台完成只更新那只宠的标记；停止会中断当前工作并暂停该对话的待处理队列，用户明确继续后才往下做。上述停止语义是本设计提出的扩展，不能等同于当前实现。

这条完整链路及另外 17 个困难场景见 [journeys.md](./journeys.md)。原型的回复、保存与恢复为模拟；其实际证据和原生实验限制见 [prototype-results.md](./prototype-results.md)。
