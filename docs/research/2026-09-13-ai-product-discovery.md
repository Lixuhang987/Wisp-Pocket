# AI 个人开发中的产品发现与人工决策

核验日期：2026-09-13。本文是跨项目工作流的研究依据与建议，不是 Wisp Pocket 的需求规格或已验证产品结论。
当前目标：先解决开发者自己的真实问题，再通过少量外部使用证据修正设计，并形成诚实、可复述的面试案例；暂不以证明市场规模为目标。

## 外部方法事实

- SVPG 将产品风险分为价值、可用性、技术可行性、业务可持续性；强调尽早处理风险，围绕用户与业务结果工作。[1]
- Teresa Torres 的机会解决方案树串联“期望结果 → 用户需要、痛点或愿望 → 备选方案 → 假设测试”。机会应来自具体过往经历，不能凭空生成；她建议先收集 3–4 个用户故事，再开始组织与持续修订机会空间。[2]
- 假设测试针对方案成立所需的具体条件；优先测试“对成功至关重要、现有证据又不足”的假设，无需逐条测试所有假设。[3]
- 应比较多个方案，并在测试前写下成功标准；综合多项证据调整或淘汰方案。一次失败可能意味着修改设计，也可能意味着应换一个问题。[3]
- GOV.UK 的主持式可用性测试要求观察真实或潜在用户完成具体任务。任务要有真实情境和清晰目标，不暗示操作路径；主持人主要观察和聆听。[4]
- GOV.UK 建议按研究问题组织小轮研究；访谈、可用性测试等每轮通常 4–8 人，证据不清时继续迭代。它将这与需要更大样本的问卷、A/B 测试及基准评估区分开。[5]

## 方法如何指导个人项目

以下是应用建议，不是来源对 AI 效果或自动化比例的保证；具体关口、交付物和起步安排见 [跨项目执行模板](./ai-product-workflow.md)。

| 方法依据 | 应用原则 |
| --- | --- |
| 四类风险需要不同证据 [1] | 一次锁定一个场景和主要风险；代码能跑不能直接回答是否值得做 |
| 机会来自具体真实经历 [2] | 先记录自用发生过的困难；AI 整理外部线索，人确认问题语境 |
| 比较方案，测试关键假设 [3] | 用现有做法作对照，先测影响大且证据少的假设；按风险选择观察、交互原型或技术试验，只有交互取舍需要时才制作两版原型 |
| 观察真实任务而非指导操作 [4] | AI 准备材料和预检，人关注参与者实际卡点；“喜欢”不能替代完成任务的观察 |
| 研究应随问题迭代 [5] | 验证结果决定继续、调整或停止；无需在开始编码前一次写完全部产品规格 |

人工关口是需要判断的时刻，可以合并，不必形成多次会议。AI 每次提交决策卡、可操作产物及关键证据；人决定目标、方向、风险和投入。
已确定的视觉规范、组件规则、布局检查和正常修复由 AI 执行；涉及价值判断、证据冲突、体验取舍或超出范围时再交给人。
代理扮演用户或相互评审可以发现遗漏、提出假设，但不能记为真实访谈、外部需求证据或真实任务成功率。

## 证据强弱与验证边界

- **原始观察**：自己或真实参与者在具体情境做了什么、在哪里卡住、原话是什么；保留时间、情境、记录位置及适用人群。
- **解释与推断**：AI 对观察的归类、因果猜测、优先级建议；每条关联原始证据，允许人推翻。
- **待验证假设**：尚未观察到的需求、预期效果、模拟人物反馈；不能因为重复出现在报告中就升级为事实。
- 自己是首位真实用户，自用日志能够支持“对我有用”；由于已有产品知识与个人偏好，它不能证明外部新用户会用或存在广泛需求。
- 外部评论和竞品评价可帮助找到线索，但通常缺少完整使用情境；先用于形成研究问题，不直接当作本产品需求。
- 初次可约 3–5 位有相似情境的人做一小轮；资源只有 2–3 人时也能先发现问题。这是个人资源下的起步建议，不是官方样本门槛，也不能据此证明市场需求或统计提升。
- 测试前写清目标、成功条件和允许的帮助程度；分别记录独立完成、需要提示、未完成。任务耗时和卡点可描述这轮表现，不应外推总体成功率。
- 对比改动前后时保留任务、参与者、测试顺序等差异；同一人再次尝试可能有学习效应，不能把全部改善归因于设计。

## 失败回路

1. 页面、布局或交互明显出错：AI 根据预检直接修复，再交付人走关键路径。
2. 真实用户不理解入口或流程：回到对应交互假设，修改原型后再测，不立即扩充功能。
3. 用户理解并能完成，但实际情境不需要或仍选原办法：回到问题价值与替代办法，必要时换问题。
4. 多个方案都表现不好：检查原始问题是否理解错，而不是增加更多视觉变体。
5. 原型好用但实现代价超出时间预算：缩小范围或做技术可行性验证，再决定是否实施。

## 面试证据与待验证假设

- 案例保留“真实问题 → 证据 → 未采纳方案及理由 → 原型 → 观察到的困难 → 设计改动 → 已知限制”；展示经过参与者允许且去标识的信息。
- 可以展示真实任务记录和失败后的修改；没有测量就不填“提升百分比”，没有外部采用就不称“验证了市场需求”。
- 待验证：这套流程能否减少本人逐项核验的时间，同时保留对核心判断的控制；先在一个小场景试完一轮，再调整介入点。
- 待验证：自用问题是否同样困扰其他人、哪些情境最值得扩展、原型收益能否延续到长期真实使用；当前均无本项目数据支持。
