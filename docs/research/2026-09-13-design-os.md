# Design OS：核心理念、设计流程与交接边界

核验日期：2026-09-13。取证版本为官方仓库 `main` 的 [529dedb43bfec24b2cbb128f26dd8cbc6143f754][commit]。本文通过 GitHub API 阅读官方命令、技能、文档与界面源码；未安装或执行 Design OS，生成质量与运行效果未实测。研究不代表 Wisp Pocket 已采用这些流程。

## 它是什么

Design OS 定位为产品规划与设计工具：在独立工作区定义产品、设计界面，再导出到实际产品仓库实现。仓库包含提供预览与进度展示的 React 应用、流程命令，以及负责视觉质量的 `frontend-design` 技能；把整个项目理解成一份 `SKILL.md` 会漏掉它的工件与交接流程。[官方职责说明][agents]、[技能目录][skills]、[界面数据加载][loader]

当前技能的规范位置是 `.agents/skills/frontend-design/SKILL.md`，`.claude/skills` 通过符号链接指向它；阶段流程则位于 `.claude/commands/design-os/`。`/design-screen` 明确要求读取并应用 `frontend-design`，后者强调明确的审美方向、排版、配色、空间与细节。[变更记录][changelog]、[屏幕命令][screen]、[视觉技能][frontend]

## 核心理念

以下是基于官方流程的归纳：

- **先把产品和体验说清楚，再做生产集成。** 先确定用户、问题、功能与界面，再把已有设计交给实现 agent；后端架构和业务逻辑在目标仓库决定。[职责与交接边界][agents]
- **全局约束先统一，功能按模块收敛。** 产品总览回答“是什么、为什么”；roadmap 拆出优先级明确、可相对独立设计的 section；全局 data shape 统一实体名称与概念关系；tokens 与 shell 统一视觉和导航。[产品定义][vision]、[全局数据形状][data]
- **用真实感数据把设计变成具体问题。** 每个 section 明确用户动作、信息、流程与范围，随后生成示例数据与 TypeScript 类型；示例要含长文本、不同状态、空数组等，以便设计面对实际内容。[模块规格][shape]、[示例数据][sample]
- **界面本身也是可交付工件。** 使用 React 组件形成可预览的设计；组件接收数据 props、发出操作 callbacks，预览层注入示例数据。这样视觉设计和生产数据接入有明确接口。[屏幕设计][screen]
- **把上下文与验收要求一起交接。** 输出包含组件、需求、类型、设计 tokens、截图、实施提示词与行为测试规格，帮助后续 agent 理解设计意图和预期用户流程。[导出命令][export]

## 当前推荐流程

命令名称沿用官方说明中的写法。推荐主线是：

```text
/product-vision → /design-tokens → /design-shell
→ 每个 section：/shape-section → /design-screen → 预览与调整 → 可选 /screenshot-design
→ /export-product → 复制到产品仓库 → Shell → 逐 section 实现与验证
```

| 步骤 | 主要工作与产物 | 用户参与点 |
| --- | --- | --- |
| `/product-vision` | 明确产品、优先级与实体；一次生成 `product-overview.md`、`product-roadmap.md`、`data-shape/data-shape.md`，都在 `product/` 下。[来源][vision] | 先收集想法，再逐步澄清；信息足够后直接写三份文件，随后评审和修改。 |
| `/design-tokens` | 选择 Tailwind 调色板和 Google Fonts，生成 `product/design-system/` 下的颜色、字体 JSON。[来源][tokens] | 用户选择偏好，汇总确认后保存。 |
| `/design-shell` | 定义全局布局、导航、用户菜单与响应式行为；生成 `product/shell/spec.md`、`src/shell/components/` 和预览层。[来源][shell] | 选择布局，澄清细节，确认 shell 规格后生成。 |
| `/shape-section` | 定义一个功能模块的用户流程、UI 要求和范围；一次生成该 section 的 `spec.md`、`data.json`、`types.ts`。[来源][shape] | 选择模块、回答澄清问题；有 shell 时确定该模块是否独立展示；信息足够后直接生成，再评审。 |
| `/design-screen` | 根据规格、数据与类型生成可导出的 React 组件及独立预览层；应用产品 tokens、响应式与深浅主题要求。[来源][screen] | 多视图时先确定做哪一个；完成后预览调整，重复命令补齐其他视图。 |
| `/screenshot-design` | 为指定视图保存 PNG 参考图到 `product/sections/`；此命令要求 Playwright MCP。[来源][screenshot] | 多个设计时选择目标，可额外记录不同主题或状态。 |
| `/export-product` | 生成 `product-plan/` 和 `product-plan.zip`，包含 UI 资产、规格、实施指引与测试规格。[来源][export] | 在目标仓库回答技术栈、鉴权、集成等问题，再进行实施和逐阶段评审。 |

`/product-roadmap`、`/data-shape`、`/sample-data` 仍可独立生成或修改对应工件，但初次流程已由 `/product-vision` 与 `/shape-section` 合并生成。这个简化来自 2026-02-09 的变更，不能把旧版较长命令清单当成当前每次必跑的步骤。[变更记录][changelog]

这条主线允许不完整导出：最低条件是产品总览、roadmap、至少一个有屏幕设计的 section；全局 data shape、tokens、shell 是推荐项。导出命令和 Export 页的判断一致，因此可以先交接一部分界面。[导出前置条件][export]、[Export 页实现][export-ui]

## 交付物与生产实现的边界

| 设计阶段交付 | 目标产品仓库继续完成 |
| --- | --- |
| 有样式的 React shell 与 section 组件 | 接入实际路由、状态管理和业务逻辑；将 callbacks 连接到真实操作。 |
| 全局实体词汇、UI `types.ts` 与示例数据 | 决定数据库模型、数据获取与持久化，用真实数据满足组件接口。 |
| 产品需求、用户流程、视觉参考与 tokens | 完成实际业务状态，验证加载、失败、空态、响应式与视觉一致性。 |
| 各 section 的 `tests.md` | 选择测试框架，编写并运行测试；这些 Markdown 文件描述验收行为，不是已运行的测试代码。 |

以上边界来自[交接模板][export]与[官方实施文档][implementation]。全局 data shape 明确只描述核心实体和概念关系，不提前规定字段、验证规则或数据库 schema；section 类型则定义 UI 需要的数据接口，后端可以组合、拆分和扩展。[数据形状命令][data]、[导出数据契约][export]

预览 wrapper 只服务 Design OS：它导入示例 JSON，示例回调可只记录 `console.log`。导出时只保留组件并调整导入路径，wrapper 不进入产品仓库；因此能看到界面和点击反馈，并不证明真实业务已接通。[屏幕命令][screen]、[导出转换][export]

官方推荐按里程碑实施：先 `01-shell.md` 配好 tokens 与导航，再从第 02 个里程碑起逐 section 实现，每步评审和测试；也提供 one-shot 提示词，要求实现 agent 先读资料、提问、制定计划。官方将组件定位为可直接接入的完整 UI；这属于交付目标，本次未验证任何一次生成结果达到生产质量。[实施文档][implementation]、[导出提示词][export]
